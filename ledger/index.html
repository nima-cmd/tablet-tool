Chapter I

Foundations & Setup

Milestone 0 — getting comfortable with the terminal and Python, and installing our two tools.

Terminal basics

  • whoami — prints your username. Proves the basic loop: you type, it answers.
  • pwd — "print working directory": which folder the terminal is currently in.
  • ls — lists files/folders in the current directory.
  • cd <folder> — "change directory." Looks relative to where you currently are — cd tablet-tool fails if you're not already in the folder that contains it; step in one folder at a time, or give a full path like cd Projects/tablet-tool.
  • The prompt itself (e.g. ~/Projects/tablet-tool$) always shows your current location.

Python — two ways to run it

  • python3 alone — opens the REPL (Read-Eval-Print-Loop): type one line, see the result immediately. Great for experimenting. Exit with exit() or Ctrl-D.
  • python3 src/somefile.py — runs a whole script file at once. This is how real programs live: saved, editable, rerunnable.
  • Rule of thumb: REPL to experiment, script to keep.

Packages & permissions

  • sudo apt install -y <package> — installs software via Pop!_OS's package manager. sudo = run as administrator, -y = don't ask for confirmation.
  • python3-evdev — a library (code you import into your own scripts) for reading input devices.
  • xdotool — a program (run by name, or launched from code) for sending keystrokes/clicks.
  • Users & groups — hardware devices under /dev/input/ are owned by a group (usually input). sudo usermod -aG input $USER adds your account to that group so you can read the tablet without sudo. Requires logging out/in to take effect. Check membership with groups.
Chapter II

Detecting Button Presses

Milestone 1 — opening the tablet's Pad and printing which express key was pressed.

Core Python building blocks

  • import x / from x import y, z — pulls code from a library into your file. from evdev import InputDevice, list_devices grabs only those two named tools out of the whole evdev library.
  • Variable — a name holding a value, e.g. path = "/dev/input/event5".
  • List — an ordered bunch of values in [...]. list_devices() returns a list of device path strings.
  • for loop — for path in list_devices(): runs its body once per item, with path set to each one in turn. The loop header is where the variable gets declared and reassigned each pass — there's no separate declaration step in Python.
  • Object & dot notation — InputDevice(path) builds an object bundling data about that device; device.name / device.path read specific pieces off it with a dot.
  • if / string membership — if "Pad" in device.name: is True when that exact substring appears anywhere inside the bigger string. Case-sensitive: "pad" and "Pad" are different checks entirely.
  • None as a placeholder — pad = None means "nothing found yet"; if pad: is only True once it holds a real object, not None.

evdev specifics

  • list_devices() — asks the OS for every input device path currently on the machine.
  • InputDevice(path) — opens a path as a device object.
  • device.name — the human-readable device name (e.g. "Hanvon Ugee Deco Pro MW Pad" over the wireless dongle, or "UGTABLET Deco Pro MW Pad" over USB-C cable — the same physical device can report different names depending on connection mode, which is exactly why matching on a substring like "Pad" is safer than an exact match).
  • device.read_loop() — gives an endless stream of events from that one device. Blocks (waits patiently, no CPU burned) until the next event arrives. Runs forever — stop it yourself with Ctrl-C, which raises a KeyboardInterrupt (the traceback you see on Ctrl-C is expected, not a bug).
  • Event anatomy — every event has:
    • type — what kind of thing happened. Key ones used so far: EV_KEY (a button/key), EV_REL (relative motion, e.g. the Pad's dial), EV_MSC (misc scan-code metadata, safe to ignore).
    • code — which specific button/axis. E.g. 256–263 for our 8 Pad express keys; 320 (BTN_TOOL_PEN, proximity, not a real click), 330 (BTN_TOUCH, the pen tip touching down), 331/332 (BTN_STYLUS/BTN_STYLUS2, the two real barrel buttons).
    • value — for EV_KEY: 1 = pressed down, 0 = released, 2 = held/auto-repeat. For EV_REL (the dial): a movement amount, not a press state at all.
  • from evdev import ecodes + event.type == ecodes.EV_KEY — readable names for these numeric type constants instead of memorizing raw numbers.
  • Why filter to value == 1 — acting only on the press edge guarantees one tap = one action, not a down-and-up pair, not repeats while held.
  • evtest (sudo evtest) — a tool that talks directly to the kernel, bypassing our Python entirely. Useful for isolating "is this a code problem or a hardware/driver problem?"

Debugging lessons learned

  • Indentation in Python is the block structure, not decoration — dedenting a line by mistake changes what it's nested inside of, silently changing behavior (bit us more than once: firing logic ending up outside the loop it was meant to be inside).
  • == (compare) vs = (assign) — the #1 beginner mixup. if event.value == 1 asks a question; event.value = 1 would (wrongly) assign.
Chapter III

Mapping Buttons to Shortcuts

Milestone 2 — press a button, fire a real keyboard shortcut via xdotool.

Keystrokes

  • A keystroke = one key. A shortcut = a key plus modifiers (ctrl, shift, alt, super), written with +: ctrl+z, ctrl+shift+z.
  • xdotool key <combo> — press-and-release a keyboard shortcut, e.g. xdotool key ctrl+z.
  • xdotool click <button> — a mouse click, not a keyboard combo. Button 3 = right-click.
  • xdotool type "<text>" — types literal text.
  • Symbol keys sometimes need their full keysym name, not the raw character: bracketleft/bracketright for [/]; function keys need capital letters, F4 not f4. All xdotool key names are case-sensitive.
  • xdotool acts on whatever window currently has focus — same as your real keyboard. sleep N (shell) or time.sleep(N) (Python) buys time to click into the target app before it fires.

Running programs from Python

  • import subprocess + subprocess.run(["xdotool", "key", "ctrl+z"]) — runs another program from inside a script. Always pass a list of separate strings, never one combined string — a list hands each piece straight to the program with no shell re-interpreting spaces/special characters. Safer, avoids a whole category of bugs.
  • A common bug: writing "combo" (a literal string) instead of combo (the variable) — quotes change everything.

Dictionaries & config files

  • Dictionary — maps a key to a value: SHORTCUTS = {256: "ctrl+z", 257: "b"}. SHORTCUTS.get(event.code) looks up a code and returns its shortcut, or None if it's not in the dict — no crash, just nothing to fire.
  • Config vs code — code is the logic (read events, fire keys); config is your personal choices (which key does what). Separating them means rebinding a key needs zero code changes.
  • JSON — a text format for data, close to a Python dict but with quoted keys always: {"256": "ctrl+z"}. Read with import json + json.load(f); the loaded keys come back as strings, not numbers, so they need converting to match event.code.
  • Dict comprehension — {int(code): combo for code, combo in raw.items()} builds a new dict by looping over an existing one in one line. .items() gives you (key, value) pairs to loop over. Equivalent to a plain for loop that fills in a dict one entry at a time, just condensed.
  • String methods: .startswith("click:") checks a prefix; .split(":", 1)[1] splits on the first : and grabs everything after it — used to support both "ctrl+z" (implicit keyboard shortcut) and "click:3" (explicit mouse click) in the same config file, without rewriting every existing entry when adding a new kind of action.
Chapter IV

Pen, Monitor Mapping, Pressure

Milestone 3 — wrapping xinput/xsetwacom to control the pen itself.

Configuring vs reading a device

  • xinput list — lists every X11 input device (general purpose).
  • xsetwacom --list devices — lists devices specifically on the wacom X driver (which this pen is forced onto via a config rule, since the stock driver misbehaves).
  • xsetwacom --list parameters — every pen property you can tune: Area/MapToOutput (monitor mapping, upcoming), PressureCurve (pressure feel, upcoming). We deliberately do not use xsetwacom's Button/key action for shortcuts — that's the stuck-modifier bug this whole project was built to avoid. Keybindings stay the evdev+xdotool way.

Watching multiple devices at once

  • Why we got stuck: read_loop() blocks forever on one device — it never naturally returns, it just keeps waiting for that device's next event. Our first attempt had if pen: ... for event in pen.read_loop(): ... written before if pad: ... for event in pad.read_loop(): .... In practice: pen shortcuts fired correctly, but Pad shortcuts never fired at all — not because the Pad code was broken, but because execution never even reached it. The program got stuck inside the pen's "listen forever" loop, so the pad block below it never got a turn to run. You can't just stack two infinite loops back-to-back and expect both to execute — only the first ever runs.
  • import selectors — another standard-library module (same category as json/subprocess), built for "wait until any of several things is ready, then tell me which."
  • selectors.DefaultSelector() — builds a fresh "watcher" object.
  • sel.register(device, selectors.EVENT_READ) — adds a device to the watcher's list, and says "notify me when it has something readable." Can register several devices on one watcher.
  • while True: for key, mask in sel.select(): — an intentional infinite loop wrapping sel.select(), since select() only waits for one round of "something's ready" and then returns; wrapping it keeps asking again forever. sel.select() blocks (efficiently) until any registered device has data ready, then returns a list of (key, mask) pairs, one per device that fired.
  • key.fileobj — inside that loop, this is how you get back the actual device object (pad or pen, whichever triggered) from the pair sel.select() handed you.
  • device.read() — like read_loop(), but drains whatever's currently pending without blocking forever; it returns control once it's done, so the outer while True can loop back to sel.select() and wait for the next thing.
  • This fully replaces having a separate if pad: ... read_loop() ... and if pen: ... read_loop() ... block each with their own copy of the same combo-firing logic — one shared loop now serves whichever device actually fired. The one-time "found the pad"/"found the pen" confirmation prints stay, but move to run once up front, before the loop starts, rather than being tied to either device's own read loop.
  • Ordering matters: sel.register(pad, ...) has to come after pad is actually found (assigned from the device-search loop), not before — referencing a variable before it's assigned raises NameError, since Python runs top to bottom.

Mapping the pen to one monitor

  • xrandr --listmonitors — lists your monitors ("outputs") by name, e.g. DP-0, DP-4. By default the pen's area stretches across the entire desktop, which feels squished and has the wrong aspect ratio.
  • xinput map-to-output "<device name>" <output> — confines that device to just one monitor; X11 works out the coordinate math.
  • Two different device registries, two different names: the evdev name (what pen.name gives you, from the kernel — e.g. "UGTABLET Deco Pro MW Pen") is not always identical to the name X11/ xinput registers the same physical device under (e.g. "UGTABLET Deco Pro MW Pen stylus" — note the added " stylus"). Substring matching ("Pen" in device.name) works fine across both layers, but an exact name match (like map-to-output needs) must use the exact string from whichever layer you're actually calling into.
  • Writing your own importable module — import map_pen works exactly like import json, except map_pen is your own file (src/map_pen.py), not a built-in library. Any .py file can be imported by its filename (minus .py) from another file in the same folder.
  • Defining your own function — def map_to_monitor(pen_name, output="DP-0"): bundles reusable logic under a name you call later, the same idea as print() or open() except you wrote it. pen_name and output are parameters — values the caller supplies each time; output="DP-0" gives that parameter a default value, used only if the caller doesn't supply one.
  • JSON has no comment syntax at all — not #, not //, nothing. A stray #comment line at the top of a .json file breaks json.load immediately (JSONDecodeError: Expecting value), even though the same habit is totally normal and expected in a .py file.
  • Structuring config beyond one flat dict — once you need more than one kind of setting (button shortcuts and a monitor name), nest them under named keys instead of mixing everything into one flat object: {"shortcuts": {"256": "ctrl+z", ...}, "monitor": "DP-0"}. Reach one level deeper when loading: raw["shortcuts"].items() instead of raw.items(). Dictionary/JSON keys are exact, case-sensitive strings — raw["Shortcuts"] and raw["shortcuts"] are different keys, same trap as "Pad" vs. "pad" back in Lesson 1.3.

Shaping the pressure curve

  • The pen reports pressure as a raw number; the pressure curve decides how that raw number maps to actual output (line thickness/opacity). Softer = light touches do more, firmer = you must press harder. Genuinely personal, worth tuning by feel.
  • xsetwacom --get "<pen name>" PressureCurve / xsetwacom set "<pen name>" PressureCurve a b c d — four numbers (0–100), two Bézier control points. 0 0 100 100 is linear (the baseline); lowering the second number (e.g. 0 10 80 100) softens it — output hits max sooner, before input reaches 100%; raising the first/lowering the last (e.g. 10 0 100 90) firms it up — more pressure needed for the same effect.
  • List comprehension — [str(n) for n in curve] is the list-building twin of the dict comprehension from Milestone 2: loop over curve, convert each number to a string, collect the results into a new list. Needed because subprocess.run requires a list of strings, not numbers.
  • list1 + list2 — joins two lists into one combined list; used to glue the fixed part of an xdotool-style command (["xsetwacom", "set", pen_name, "PressureCurve"]) onto the converted curve numbers.
  • Importing a module isn't the same as using it — a real gotcha we hit: import pressure at the top of a file doesn't error even if nothing below actually calls anything from it. Just because a script runs with no crash doesn't mean every piece you added is actually wired up — check that you both read the relevant config value (PRESSURE_CURVE = raw["pressure_curve"]) and call the function (pressure.set_pressure_curve(...)) somewhere real code paths reach.
